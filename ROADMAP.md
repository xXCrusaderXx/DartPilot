# Roadmap

This roadmap is a **living document**. Phases, features, and their order change as the project learns. New ideas are welcome at any time; see [Proposing changes](#proposing-changes).

Every milestone carries a version `vX.Y.Z – Name`, and **closing one creates a release** (see [Releases](#releases)). Versions follow the order in which the milestones are expected to finish:

- **0.1 to 0.6 – Detection.** They follow section 10 of the [technical plan](docs/technical_plan.md#10-first-implementation-plan) (its phase 1 is split into 0.1 to 0.3) and are the critical path: each ends with a measured result.
- **0.7 to 0.9 – Platform and app.** Remote play, the engine on Android and Windows, and the app as a dart companion. Work on them runs in parallel to detection; what is finished early ships with the next release.
- **1.0 – Product integration.** Phase 5 of the plan: everything above together, packaged and documented.

If a milestone becomes ready before one with a lower version, it waits, or the open milestones are renumbered before the release, so that releases always go up.

Every work item is an issue in its [milestone](https://github.com/xXCrusaderXx/DartPilot/milestones) with a "Done when" criterion. Labels: `prio/high` (next up), `prio/medium`, `prio/low`; `status/blocked` with the reason in the issue; `area/*` for the module, `experiment` for measurements with a documented result, `decision` for work that ends in an [ADR](docs/adr).

### Detection

| ------- | ---------- | ------- | ------ |
| **[0.1.0 – Capture & timing](https://github.com/xXCrusaderXx/DartPilot/milestone/1)** | 1 Measurability | Documented camera hardware and capture settings. Capture backend and timestamp source chosen. One capture thread and bounded ring buffer per camera. Per-frame IDs, capture and arrival timestamps, drop detection. Session recording. Capture health statistics. Developer GUI for camera setup and live diagnostics ([ADR 0003](docs/adr/0003-developer-gui.md)). | Three cameras are recorded reliably, and their FPS, drops and latency are known. |
| **[0.2.0 – Replay & board model](https://github.com/xXCrusaderXx/DartPilot/milestone/2)** | 1 Measurability | Replay format and throw ID. Deterministic replay with a CI check. Python reader. Board coordinate and ground-truth convention. Deterministic scorer. Intrinsic calibration without a user-held target: a prior per camera model, refined per camera from the dartboard together with the extrinsics ([ADR 0006](docs/adr/0006-calibration-without-user-held-targets.md)), validated against a per-camera ChArUco reference. Extrinsic calibration from the dartboard itself: wire detection, measured board model, pose per camera, validated against held-out points, cross-camera consistency and reference pins. | Recorded sessions replay identically, anyone can calibrate their cameras at home with a documented error budget, and board points can be scored. |
| **[0.3.0 – Ground truth & baseline](https://github.com/xXCrusaderXx/DartPilot/milestone/3)** | 1 Measurability | Ground-truth method with measured uncertainty. Annotation tool. First benchmark dataset, split by session. Benchmark metrics and report. Baseline frame-differencing pipeline. Baseline report. | A reproducible baseline that describes the current state quantitatively. **Delivered:** ADR 0011, the benchmark with flags, a dataset of 5 sessions, and the [baseline report](docs/reports/baseline-0.3.0.md). Live detection: 51 of 55 confirmed darts in the right field, 4 abstentions, none in a wrong field; baseline: 21 in a wrong field. Reference corners: median 1.33 mm. |
| **[0.4.0 – Synchronisation & geometry](https://github.com/xXCrusaderXx/DartPilot/milestone/4)** | 2 | Inter-camera offset and jitter. Timeline view. Single-camera projection error. Triangulation with reprojection and plane-distance checks. Temporal frame association. Detection of camera and board movement. Geometry path decision. | A well-founded decision on time association and the geometry path. |
| **[0.5.0 – Tip localisation](https://github.com/xXCrusaderXx/DartPilot/milestone/5)** | 3 | Candidate lists, shaft-axis estimation, confidence and pixel covariance. Annotated robustness cases. Ablation study. Optional learned detector [#31](https://github.com/xXCrusaderXx/DartPilot/issues/31). Optional dart profile: the player's darts measured as a reference; detection must work without it. | Measurably better tip localisation, or a clearly documented remaining bottleneck. |
| **[0.6.0 – Fusion & scoring](https://github.com/xXCrusaderXx/DartPilot/milestone/6)** | 4 | Uncertainty-weighted robust fusion. Abstention threshold from the validation set. Regression tests for hard throws. Latency budget. Hold-out evaluation. Experiment: a microphone as hit sensor [#127](https://github.com/xXCrusaderXx/DartPilot/issues/127). Uncertain throws shown in the app for the player to confirm [#126](https://github.com/xXCrusaderXx/DartPilot/issues/126). Pulled darts detected, ending the turn [#128](https://github.com/xXCrusaderXx/DartPilot/issues/128). Bounce-outs counted as thrown darts [#199](https://github.com/xXCrusaderXx/DartPilot/issues/199). Darts put in by hand flagged and not counted as thrown [#231](https://github.com/xXCrusaderXx/DartPilot/issues/231). Every detection value documented, recorded with each throw and adjustable [#195](https://github.com/xXCrusaderXx/DartPilot/issues/195). | A verifiable engine with traceable quality indicators. |


Ahead of the phases, a first **live detection** already runs (`dartpilot serve --cameras`): still moments of all cameras go to a dart tracker that locates each new dart from the cameras whose axes agree, abstains otherwise, and notices takeouts. A dart reaches the app about 0.5 s after it lands. Its values are being made documented and adjustable [#195](https://github.com/xXCrusaderXx/DartPilot/issues/195), with a detection test in the setup GUI for rating and tuning it live. The replay runs it next to the frame-differencing baseline (#18). The phases above measure and improve it; they do not start from zero.

## Priorities and order

The order in which work is picked up, highest first. Issue labels carry the same priorities.

1. **Releases v0.1.0 and v0.2.0:** capture and calibration are done; the calibration is validated with its error budget in [ADR 0009](docs/adr/0009-board-calibration-validated.md).
2. **Remote play** – done: engine discovery [#109](https://github.com/xXCrusaderXx/DartPilot/issues/109), phone as a remote display [#114](https://github.com/xXCrusaderXx/DartPilot/issues/114), engine choice in the app [#105](https://github.com/xXCrusaderXx/DartPilot/issues/105).
3. **Ground truth and baseline (0.3.0):** ground-truth method [#14](https://github.com/xXCrusaderXx/DartPilot/issues/14), with a guided reference measurement of the tip position in the app, annotation tool [#15](https://github.com/xXCrusaderXx/DartPilot/issues/15), benchmark metrics [#17](https://github.com/xXCrusaderXx/DartPilot/issues/17); then the dataset [#16](https://github.com/xXCrusaderXx/DartPilot/issues/16), the baseline pipeline [#18](https://github.com/xXCrusaderXx/DartPilot/issues/18) and its report [#19](https://github.com/xXCrusaderXx/DartPilot/issues/19); corrections from play as labelled data and replay through the API [#115](https://github.com/xXCrusaderXx/DartPilot/issues/115).
4. **Platform groundwork:** PIN pairing [#110](https://github.com/xXCrusaderXx/DartPilot/issues/110), portable data directory and camera identity [#112](https://github.com/xXCrusaderXx/DartPilot/issues/112), Raspberry Pi host [#108](https://github.com/xXCrusaderXx/DartPilot/issues/108).
5. **Android:** the feasibility spike [#104](https://github.com/xXCrusaderXx/DartPilot/issues/104) succeeded (three cameras at 30 fps on a phone, each with its own clock to map); next the Android engine [#106](https://github.com/xXCrusaderXx/DartPilot/issues/106).
6. **Synchronisation and geometry (0.4.0):** inter-camera timing [#20](https://github.com/xXCrusaderXx/DartPilot/issues/20) can start any time; the rest needs the 0.3.0 dataset. The microphone experiment [#127](https://github.com/xXCrusaderXx/DartPilot/issues/127) when there is room.
7. **App:** one game on several displays [#116](https://github.com/xXCrusaderXx/DartPilot/issues/116), profiles and statistics [#117](https://github.com/xXCrusaderXx/DartPilot/issues/117) with precision statistics and training modes on top [#125](https://github.com/xXCrusaderXx/DartPilot/issues/125), throw replay [#129](https://github.com/xXCrusaderXx/DartPilot/issues/129) (its camera crops need the throw's frames from the engine), then lobbies and friends [#124](https://github.com/xXCrusaderXx/DartPilot/issues/124): identity and pairing first; how players connect over the internet is decided in its own ADR before online play is built.
8. **Tip localisation (0.5.0)** – including the optional dart profile [#120](https://github.com/xXCrusaderXx/DartPilot/issues/120) after generic detection is checked against a second dart type – **fusion (0.6.0)** with confirming uncertain throws [#126](https://github.com/xXCrusaderXx/DartPilot/issues/126) first and pulled-dart detection [#128](https://github.com/xXCrusaderXx/DartPilot/issues/128) on the board check of #121, then **1.0.0** with camera health [#130](https://github.com/xXCrusaderXx/DartPilot/issues/130), and later ring light [#131](https://github.com/xXCrusaderXx/DartPilot/issues/131) and dataset donation [#133](https://github.com/xXCrusaderXx/DartPilot/issues/133); Windows [#107](https://github.com/xXCrusaderXx/DartPilot/issues/107), CI for Android and Windows [#111](https://github.com/xXCrusaderXx/DartPilot/issues/111) more game modes [#118](https://github.com/xXCrusaderXx/DartPilot/issues/118) and the score caller [#132](https://github.com/xXCrusaderXx/DartPilot/issues/132) when there is room.

Phases after 1.0.0 are open. Ideas that don't belong to a phase yet are collected below.

## Open ideas

Unscheduled proposals, in no particular order. A maintainer moves an idea into a milestone once it is clear and someone works on it.

- Online multiplayer (after 1.0.0): apps of different households play together, each with its own engine.
- iOS app as a remote display (iOS cannot run the engine with USB cameras, ADR 0008).
- Public benchmark dataset with a leaderboard of detection variants.
- Neural tip detector, if classical candidates turn out to be insufficient (phase 3 decides).

Add ideas through a [roadmap proposal](https://github.com/xXCrusaderXx/DartPilot/issues/new?template=roadmap_proposal.yml).

## Proposing changes

- **New feature or change to a phase:** open a [roadmap proposal](https://github.com/xXCrusaderXx/DartPilot/issues/new?template=roadmap_proposal.yml). Proposals are discussed in the issue. Accepted ones get a milestone, or land under [Open ideas](#open-ideas).
- This file is updated in the same PR that changes a milestone.

## Releases

- Work happens on feature branches that are merged into `dev`. At a release point, `dev` is merged into `main` by the maintainer.
- Closing a milestone `vX.Y.Z – Name` starts the `Milestone release` workflow. It checks that every issue in the milestone is closed, collects the closed issues and pull requests as release notes, and runs the `Release` workflow for version `X.Y.Z` on `main`.
- The `Release` workflow builds and tests the engine, builds the player app for every platform, and publishes GitHub release `vX.Y.Z` with the Linux AppImage (app and engine, built on Ubuntu 22.04 with a static OpenCV and checked for missing libraries on clean Ubuntu, Debian and Fedora systems), the Android APK, the Windows app as a zip (without an engine), the web app as a zip, the source archive, and `SHA256SUMS` over all of them. Every package carries the release version (`--build-name`, `DARTPILOT_VERSION`). A manual run without a version is a dry run: it builds and checks everything and publishes nothing.
- The APK is signed with the release key from the repository secrets `ANDROID_KEYSTORE_BASE64` (the keystore, base64), `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS` and `ANDROID_KEY_PASSWORD`. Without them it is signed with a debug key and the run shows a warning; such an APK cannot be updated by one signed with the release key, so the key must be in place before the first public APK and never change.
- If a milestone is closed by mistake while issues are still open, no release is made. Reopen the milestone, finish the issues, and close it again.
- Bug-fix releases (`X.Y.Z+1`) use their own small milestone, or a manual run of the `Release` workflow.
- Engine, app and tools carry one version; between releases it is the next one with `-dev` (CONTRIBUTING.md, "Versions").
